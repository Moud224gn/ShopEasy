# Internationalization — Multi-locale, RTL, Multi-currency

> Document détaillé référencé par `CLAUDE.md` §8.
> **Lis ce fichier avant d'ajouter du texte utilisateur, un format date/devise, ou un montant.**

L'i18n n'est pas une feature, c'est une fondation. ShopEasy cible plusieurs marchés (Québec → Canada → Europe francophone → Maghreb → Afrique Ouest/Est → Afrique du Sud). L'architecture est prête dès le Sprint 1.

## 1. Locales

### Sprint 1 — livrées
- **FR** (français) — défaut Québec, Europe francophone, Afrique francophone
- **EN** (anglais) — défaut international

### Extensible (archi prête, locales ajoutées à la demande)
- **AR** (arabe) — RTL, marchés Maghreb
- **ES** (espagnol) — marchés latino-américains
- **PT** (portugais) — Brésil, Afrique lusophone
- **SW** (swahili) — Afrique de l'Est

Ajouter une locale = ajouter un dossier de traduction + entrée config. **Aucun code applicatif modifié.**

Slash command : `/locale-add <code>` génère la structure proprement.

## 2. Frontend — next-intl

### Structure des fichiers de traduction
```
apps/web/messages/
├── en/
│   ├── common.json
│   ├── auth.json
│   ├── catalog.json
│   ├── cart.json
│   ├── checkout.json
│   ├── orders.json
│   ├── vendor.json
│   └── errors.json
└── fr/
    └── [mêmes namespaces]
```

### Convention de clés
- `kebab-case` hiérarchique
- Exemples : `cart.empty-state.title`, `errors.payment.declined`, `auth.register.tos-agreement`
- Pas de clés génériques (`label`, `button`) — toujours contextualisées (`cart.checkout-button`).

### Usage
```typescript
// Server Component
import { getTranslations } from 'next-intl/server';
const t = await getTranslations('cart');
return <h1>{t('empty-state.title')}</h1>;

// Client Component
import { useTranslations } from 'next-intl';
const t = useTranslations('cart');
return <button>{t('checkout-button')}</button>;
```

### Routing localisé
- URLs : `/fr/catalogue/...`, `/en/catalog/...`
- Jamais de query string (`?lang=fr`).
- Slugs traduits : `produit` (FR) ↔ `product` (EN). Mapping dans config.

### Détection de locale (ordre de priorité)
1. Cookie `NEXT_LOCALE` (préférence utilisateur explicite)
2. Header `Accept-Language`
3. Géolocalisation IP (Québec/Maghreb/etc. → FR, autres → EN)
4. Fallback : EN

### Formatage natif
- **Dates** : `useFormatter().dateTime(date, { dateStyle: 'long' })`
- **Nombres** : `useFormatter().number(value)`
- **Devises** : `useFormatter().number(amount, { style: 'currency', currency: 'CAD' })`
- **Relatif** : `useFormatter().relativeTime(date)` (ex: "il y a 3 jours")

Jamais de `.toLocaleString()` direct sans locale. Jamais de concaténation manuelle (`"$" + price`).

### Pluralisation ICU MessageFormat
```json
{
  "items-count": "{count, plural, =0 {Aucun article} one {# article} other {# articles}}"
}
```

```typescript
t('items-count', { count: 3 }); // "3 articles"
t('items-count', { count: 0 }); // "Aucun article"
```

## 3. Backend — Django gettext

### Messages d'erreur API et notifications
```python
from django.utils.translation import gettext_lazy as _

class OutOfStockError(APIException):
    default_detail = _("Cet article n'est plus disponible.")
```

- `gettext_lazy` dans les modèles et constantes (chargé au démarrage).
- `gettext` (alias `_`) dans les vues et services (résolu par requête).

### Fichiers de traduction
```
apps/api/locale/
├── en/LC_MESSAGES/
│   ├── django.po
│   └── django.mo
└── fr/LC_MESSAGES/
    └── ...
```

Commandes :
- `make i18n-extract` (à la racine de l'API) → extrait nouvelles chaînes via `makemessages`.
- Traducteurs éditent les `.po`.
- `make i18n-compile` → compile en `.mo`.

### Middleware
`LocaleMiddleware` lit le header `Accept-Language` et active la locale pour la requête.

### Réponse API
Chaque réponse contient :
```json
{
  "data": {...},
  "language": "fr"
}
```
Permet au frontend de détecter incohérences et de loguer si nécessaire.

## 4. RTL — architecture prête dès maintenant

L'arabe sera ajouté plus tard, mais l'architecture l'anticipe **dès le Sprint 1**. Toute UI codée maintenant doit fonctionner en RTL sans modification.

### Règle d'or : logical properties uniquement

| Interdit (physical) | Obligatoire (logical) |
|---|---|
| `margin-left` | `margin-inline-start` (`ms-*` Tailwind) |
| `margin-right` | `margin-inline-end` (`me-*` Tailwind) |
| `padding-left` | `padding-inline-start` (`ps-*` Tailwind) |
| `padding-right` | `padding-inline-end` (`pe-*` Tailwind) |
| `left: 0` | `inset-inline-start: 0` (`start-0` Tailwind) |
| `right: 0` | `inset-inline-end: 0` (`end-0` Tailwind) |
| `text-align: left` | `text-align: start` (`text-start` Tailwind) |
| `text-align: right` | `text-align: end` (`text-end` Tailwind) |
| `border-left` | `border-inline-start` |

`margin-top`, `margin-bottom`, `padding-top`, `padding-bottom` restent inchangés (axe block, indépendant du sens d'écriture).

### Configuration Tailwind
Le plugin `tailwindcss-rtl` est actif. Les classes logiques sont disponibles par défaut.

### Icônes directionnelles
Icônes à flipper en RTL : chevrons, flèches retour, indicateurs de tri, breadcrumb separators.
Icônes universelles (pas de flip) : panier, recherche, lock, user, settings.

Pattern pour les icônes directionnelles :
```tsx
<ChevronRight className="rtl:rotate-180" />
```

### Composants conditionnels au sens
Quand le layout dépend du sens, utiliser le variant `rtl:` Tailwind :
```tsx
<div className="rtl:flex-row-reverse">...</div>
```

À utiliser avec parcimonie — préférer les logical properties qui se mirroirent automatiquement.

### Tests RTL
`make test-rtl` exécute des snapshots Playwright avec `<html dir="rtl">` sur les composants principaux. Une régression visuelle = blocking.

Avant tout composant nouveau : tester visuellement en mode RTL via DevTools (`document.documentElement.dir = "rtl"`).

## 5. Multi-currency — architecture

### Principe de stockage
Tout montant est stocké en **plus petite unité de la devise** + code ISO 4217.

```python
# Backend (Django + py-moneyed)
from djmoney.models.fields import MoneyField

class Product(models.Model):
    price = MoneyField(max_digits=12, decimal_places=2, default_currency='CAD')
```

```typescript
// Frontend (dinero.js v2)
import { dinero, toDecimal } from 'dinero.js';
import { CAD } from '@dinero.js/currencies';

const price = dinero({ amount: 1999, currency: CAD }); // 19.99 CAD
```

Stockage en base : `{ amount: 1999, currency: "CAD" }`. **Jamais** un `float`, **jamais** un `Decimal` nu sans devise associée.

### Devises supportées
- **Sprint 1** : CAD (Canada), USD (international), EUR (Europe)
- **Extensible** : XAF (FCFA Afrique centrale), XOF (FCFA Afrique de l'Ouest), MAD (Maroc), NGN (Nigeria), KES (Kenya), ZAR (Afrique du Sud), GBP, JPY, etc.

Slash command : `/currency-add <iso>` ajoute la devise proprement (codes, formatters, taux de change).

### Conversion entre devises
- Taux de change cachés en Redis, rafraîchis quotidiennement via Celery beat (`tasks/refresh_exchange_rates.py`).
- Source : ExchangeRate-API, Open Exchange Rates, ou équivalent.
- Chaque conversion enregistre le taux utilisé (audit log) pour traçabilité.

```python
from apps.i18n.services.currency import convert

usd_price = convert(product.price, target_currency='USD')
# Retourne Money(1499, USD) avec taux du jour
```

### Opérations arithmétiques
**Jamais** d'addition/soustraction directe de `float`. Toujours via les libs Money.

```python
# CORRECT
total = sum(item.price for item in items, Money(0, 'CAD'))

# INTERDIT
total = sum(float(item.price) for item in items)  # erreurs d'arrondi, bugs business-critical
```

```typescript
// CORRECT
import { add, multiply } from 'dinero.js';
const total = items.reduce((acc, item) => add(acc, item.price), zero);

// INTERDIT
const total = items.reduce((acc, item) => acc + item.price.amount, 0);
```

### Affichage
- Toujours via formatters i18n :
```typescript
const formatted = useFormatter().number(toDecimal(price), {
  style: 'currency',
  currency: 'CAD',
});
// "19,99 $" en FR-CA, "$19.99" en EN-US
```

- Position du symbole, séparateurs décimaux/milliers : gérés automatiquement par `Intl.NumberFormat` selon la locale.

### Arrondi
- Bankers' rounding (round-half-to-even) par défaut via dinero.js / py-moneyed.
- Pour taxes et totaux légaux : suivre les règles de juridiction (TPS/TVQ Canada, TVA France, etc.) documentées dans `apps/api/shopeasy/orders/services/tax.py`.

### Devises par vendeur
Chaque vendeur déclare ses devises supportées (`vendors/models.py:Vendor.supported_currencies`).
Le frontend filtre les produits affichables selon la devise sélectionnée par l'acheteur, ou propose une conversion (avec avertissement).

Au login : ces préférences priment sur la détection automatique.

## 7. Vérifications automatiques

### `make i18n-check` (CI bloquant)
Détecte :
- Chaînes hardcodées en JSX (`<div>Bonjour</div>`).
- Chaînes hardcodées dans les réponses API.
- Clés manquantes dans une locale (présentes en FR, absentes en EN).
- Clés orphelines (présentes dans les fichiers, jamais utilisées).
- Devises hardcodées dans le code applicatif.

### Test exemple
```typescript
// apps/web/__tests__/i18n.test.ts
import frMessages from '@/messages/fr/common.json';
import enMessages from '@/messages/en/common.json';

test('FR and EN have identical keys', () => {
  expect(extractKeys(frMessages)).toEqual(extractKeys(enMessages));
});
```

## 8. Gestion des dates et timezones

- Stockage backend : **UTC** systématiquement (Postgres `timestamptz`).
- Affichage frontend : timezone utilisateur (préférence ou détection navigateur).
- Format date : via `useFormatter().dateTime()`, jamais `.toISOString()` à l'affichage.
- Formats relatifs ("il y a 2 jours") : `useFormatter().relativeTime()`.

## 9. Notifications et emails

- Templates email dans `apps/api/templates/emails/<lang>/<template>.html`.
- Envoi avec la locale de l'utilisateur (préférence stockée, fallback détection).
- Sujets traduits via `gettext`.
- Variables substituées via Django Template Engine, jamais de concaténation.

## 10. Anti-patterns courants

| Anti-pattern | Correction |
|---|---|
| `<h1>Welcome!</h1>` | `<h1>{t('welcome')}</h1>` |
| `errorMessage = "Invalid email"` | `errorMessage = t('errors.invalid-email')` |
| `price.toFixed(2) + " $"` | `format.number(price, { style: 'currency', currency })` |
| `new Date().toLocaleDateString()` | `format.dateTime(date)` (avec locale active) |
| `className="ml-4"` (frontend) | `className="ms-4"` |
| `Money(price * 1.15)` (taxes) | `taxService.compute(price, jurisdiction)` |
| `if (currency === 'CAD') ...` (hardcoded) | Abstraction via `supported_currencies` config |
